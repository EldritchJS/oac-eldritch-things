metallb-system                   measured; fix proposed in oac-apps#301 and tested on both clusters. Remove this line when that merges. MetalLB's own policy selects only the controller pods, leaving the operator's two uncovered; the measured need is ingress 9443 (webhooks), 8080 and 7472 (metrics) from the API server, and egress to the API server and DNS. The API server reaches the webhook over host network on the hub and through the konnectivity agent on a hosted cluster, and that agent is itself hostNetwork, so one rule covers both. speaker is hostNetwork, so none of this protects the speakers
clusters-andalusia               hub: HyperShift control plane. Ingress is closed by its four policies. Egress is open, and measures small - DNS, 443 outbound, 2379/2380 to etcd, 6443 to the other control plane - so a policy is feasible. Not written: HyperShift creates and reconciles these namespaces, and an egress deny here isolates a live hosted control plane, so it belongs with the HyperShift side rather than layered on by us. hypervisor: the KubeVirt VM namespace, open both ways, and it should stay that way. Measured 2026-11-26 with the VM deliberately started for the purpose: ACS shows the virt-launcher deployment but zero flows for it over 15 minutes, while the same cluster recorded 64 edges elsewhere in 30, so the collector is fine and this workload is the exception. The VM attaches with bridge binding on the pod network and the guest is itself an OpenShift node running its own OVN (ovn-k8s-mp0, br-int and nested veths inside the guest), so that single interface carries an entire nested cluster's traffic. A default-deny here would have to allow everything a cluster needs in order not to break andalusia, which is not a restriction worth the name. This is a permanent exception on the mechanism, not a measurement we are waiting on
